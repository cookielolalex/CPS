## P1: new conversations (M002, M004)

- The Dot creates a new conversation with its platform's "Create Thread" feature, in the same cloud environment, without the parent's history. The test conversation read and wrote files on the same VM (same `$HOME`, uid and boot id). **P1 file access: PASS.**
- **Not isolated by the platform:** the new conversation has the same app tools as the Dot, including Google Drive, GitHub, web search and message-reading tools. A generator is kept to its prompt's files only by its instructions. Whether a conversation can be created without these tools is asked in M006.
- A model selector is optional at creation; the probe used the platform default, and no verified model identifier was exposed.
- The Dot can list its conversations (with an `attachedAt` time) and read their recorded messages and turn status; a full transcript including every tool execution and the files written is **not** available. So the transcript policy is O55 (attested reading, owner check before scoring), not export.
- A completed conversation can be resumed; an archive action stops one.

## P2 and M004: Drive

- Upload limit of the Dot's Drive tool: **100 MiB per file** (a 200 MB upload failed with HTTP 413 before any write; nothing appeared). A 50 MB random file round-tripped byte for byte (upload about 12 s, download about 8 s).
- Upload responses give the file id but **no md5 and no size**; search and metadata give id, size and creation time, but **no md5 or sha256**. Confirming an upload therefore needs a download-back and a sha256 compare.
- Exact-name search returns **every copy** of a name with distinct ids (no renaming); all 20 test files were found immediately after upload (no indexing lag seen).
- `name contains` search is not a prefix filter (it returned `P10_c` for `P1_`); client-side filtering works. Folder listing can be limited to the newest N by modified time; search pages carry a page token.
- The Dot can save raw tool results into a VM file programmatically, without retyping.
- Uploads are raw files (no Office conversion); a timed-out upload can still appear, so the destination must be checked before any retry.
- The Dot's platform sometimes **refuses uploads through an automatic approval review** (with wrong reasons); the uploads went through after the owner approved. Uploads must be verified absent before a retry, and some steps may wait for the owner.

## P5: background processes (M003)

- **A detached background process does not survive the end of the tool call that started it** (zero heartbeats; verdict FAIL). The tool runs each command in its own process namespace.
- **Foreground processes do survive across tool calls**: the Dot's command tool returns a resumable session, and polling it continued the same process; holds of 60, 240, 600 and 1,200 s all completed. A 1,200 s hold is a completed process, not proof of one uninterrupted tool call.
- Consequence for the VM helper: every stage must run in the foreground with the Dot polling the same session until it exits; nothing may rely on a detached worker.

## M010: turn end, separate worker, sandbox (2026-11-11)

Recorded 2026-11-11 from the Dot's REPLY.md, checked against the message. The reply marks which output lines it kept verbatim and which it only summarized; the summary below uses the verbatim ones.

- **The probe folder could not be created without the elevated route.** The first, unprivileged setup command failed with `mkdir: cannot create directory '/home/agent/cps-m010': Read-only file system`. The Dot re-ran the setup with what the reply calls authorized filesystem escalation (the platform's elevated route), and it passed (`hold.py` sha256 `e1afe3e1…57ac5`, self-test exit 0). The owner's "yes go" (07:23:11Z, before the first attempt) approved the M010 request, which covered the hold script, the self-test, both holds and the cleanup. The reply does not say whether the escalation needed an approval of its own. Until M011 maps which paths a command can write, every command that writes under `$HOME` (setup, runner, helper) must be assumed to need the elevated route and its approval. How far one approval reaches, and whether a command prefix can be approved in advance, is asked in M011.
- **Test B (separate worker) did not run.** The Dot gave the command to a newly created native worker, which ran without the elevated route. Its first write failed (`OSError: [Errno 30] Read-only file system: '/home/agent/cps-m010/b.txt'`, `hold exit=1`), so no hold ran. It was not retried. The coordinating conversation's 1,500 s wait began after the worker had already answered, so no command ran during that wait. Whether a command survives in a separate conversation stays untested. M008's creation route is unknown, so a native worker may not match M008's set-up.
- **Test A: a command survived one wait and wake of its conversation.** The coordinating conversation started the 1,200 s hold itself (first beat 07:26:13Z). It set a one-time wake-up for 07:36:25Z, sent the "my turn ends now on purpose" note (07:26:36Z), then began a clock wait it reports as 600 s. That wait woke it at 07:36:05Z, which is less than 600 s after the note; the reply does not explain the difference. It wrote "M010 resumed" at 07:36:18Z in a clock-triggered turn, without any owner "continue M010". It polled the same session (still running), then kept polling it to the end: `hold done seconds=1200`, exit 0, 41 beats with no gap. The wake-up it had set arrived at 07:36:25Z and was ignored as a duplicate. The record does not show whether the platform counted the wait as the end of a turn. It does show that a running command survived this one wait-and-wake cycle.
- **`ps` cannot see other commands' processes.** While the hold was still running, a separate check command found no process with the hold's id (5) (`ps exit=1`). Yet polling the hold's own session showed it still running, and its file kept growing. Each command runs in its own process namespace (as P5 found), and process ids are small and repeat: every check's shell was process 2. A process id or `ps` says nothing about a command started by another command; only polling that command's own session does. Neither the helper nor the runner uses a process id to decide whether a command is still running. The helper uses its lock (`flock`) and the boot id, and the runner uses a `flock` of the job folder; both only record the process id. Process ids do name some temporary files and folders, though, so a killed command's leftover can carry the exact name the next command uses. Three such leftovers are never removed within the same boot. The runner's `.validate_<case>_<pid>` folder in the jobs folder is created without allowing an existing one, so after a killed `prepare` the next `prepare` of that case fails. The helper's temporary copy of `VM_HELPER_CONFIG.json` in `runtime/` makes the kit look changed afterwards, which is refused while a run is in flight. The `.png_stream_<pid>` file in `inbox/journal/` is simply overwritten, so it does no harm. These are fixes for helper v2.1 and the runner. `probe_p5.py` still judges liveness by process id, but it gates nothing. M011 checks that a `flock` held by one command is seen by another.
- **How earlier probes ran.** M009's commands ran in a native worker, not in the coordinating conversation. It was the mailbox worker that had claimed M009, resumed with follow-up assignments. That worker polled each command to the end without finishing its turn, while the coordinating conversation stayed free for owner messages. M008's commands ran in a separate child conversation, whose creation route the readback does not show. The scheduled mailbox checks seen between 05:22Z and 06:52Z were carried out by native workers that the coordinating conversation assigned. The check at 07:22:33Z ran in the coordinating conversation itself, found M010's fresh claim and did nothing, as the mailbox rules say. A mailbox worker also wrote M010's claim, and a mailbox worker assembled the reply after the commands had finished; the reply reports this as a deviation.
- **No visible limit** on a turn, a wait or a command. Commands of 619, 706, 1,200 and 1,800 s have completed; these are demonstrated durations, not limits.
- **What killed M008's render is still unknown.** Each set-up has been tried once. A command in the coordinating conversation (M010, across a wait and wake) completed, and so did a command in a native worker that polled it itself (M009). A command in a separate child conversation, run while the coordinating conversation waited (M008), died. One run each does not show that the set-up was the cause.
- Cleanup passed; nothing was uploaded besides CLAIM.md and REPLY.md.

**Operating rules this gives the helper's README (for the v2.1 amendment; to be confirmed by M011):** run each helper command in the foreground, through the elevated route, in the coordinating conversation that the claim names as owner, never in a worker or another conversation it starts. Poll that same session until the command exits, and prefer polling to waiting: a wait with a wake-up survived once (M010), but M008's render died while the coordinating conversation waited. A progress note or an answer to the owner is allowed while a command runs (M009, M010). Never judge a command alive or dead with `ps` or a process id. Never start a command again after it died, for example after a poll error such as `Unknown process id`: record it and let the helper's next command report it (`FOREGROUND_DIED`). If the elevated route is not approved, or a command fails with `Read-only file system`, stop, report the exact error and wait for the owner. Never retry such a command unprivileged, in another folder, or in a worker or conversation without the elevated route. Do not count on the scheduled mailbox check to wake the conversation while work is claimed: it does nothing then.

## M011: writable paths, approvals, locks across commands (2026-11-11)

Recorded 2026-11-11 from the Dot's REPLY.md, checked against the message. All test commands ran in the coordinating conversation that the claim names; a mailbox worker assembled the reply and ran one extra read-only absence check afterwards (disclosed). The reply omits the raw mount lines as platform infrastructure detail and marks which outputs it did not keep verbatim.

- **Two command routes.** The Dot's command tool takes a per-command `sandbox_permissions` value: `use_default` (the standard route) or `require_escalated` (the elevated route, which can carry a justification). It also has an optional `prefix_rule` field for a reusable command prefix; M011 left it unset, and what it would cover is unknown.
- **What the standard route can write.** `/tmp` and the command's working directory: yes. `/home/agent` and `~/cps-tools`: no (read-only file system). Through the elevated route every tested place was writable. Both routes ran as uid 1000 with the same boot id.
- **Both routes see the same files.** A line written through the elevated route under `$HOME` and in `/tmp` was read back through the standard route with the same device and inode numbers. A line the standard route wrote in `/tmp` was read back through the elevated route (that step ran no `stat`). `$HOME` and `/tmp` showed the same device and inode numbers through both routes.
- **A `flock` held by one command blocks other commands, through either route.** An elevated command locked the folder `~/cps-m011` (the runner's kind of lock). While it held the lock, an elevated probe and a standard probe were both refused; after it released the lock, both got it. Every line showed the same device and inode and the same boot id. So a `flock`, the kind of lock the runner and the helper use, holds across commands on the Dot, and a command without the elevated route sees a lock held by an elevated one. A holder through the standard route, and commands in other conversations, were not tested.
- **Elevated commands go through an automatic review.** The first elevated request did not run: the review timed out (`The automatic permission approval review did not finish before its deadline. Do not assume the action is unsafe based on the timeout alone. You may retry once, or ask the user for guidance or explicit approval.`). The one retry ran. The deadline is not shown. A request stopped in review has not run, so retrying it once is safe; this differs from a command that started and died, which must not be re-run.
- **Owner approvals were chat messages.** The owner wrote "yes go, all M series tasks are automatically approved" (08:23:33Z). At 08:25:23Z the Dot said its elevated check was waiting for the platform's approval, and at 08:26:07Z the owner wrote "Approved". By then the retried step-3 command had already run (its last line is 08:25:50Z), and so had step 4a (08:25:56Z). On this record the retry passed the automatic review without any answer from the owner. The Dot cannot see whether the platform showed the owner a prompt for any elevated command, whether any standing grant exists, or whether an approval carries over to other conversations or across a reset. It did not keep the request and start times of the elevated commands. No standing approval was created.
- **Workers and network.** The reply says a native worker can use the elevated route when its tool offers it, and cites M009's worker. M010's native worker had none. M011 did not test this. M011 ran no network command, so network access through either route is untested.
- Cleanup passed; nothing was uploaded besides CLAIM.md and REPLY.md.

**Consequence for the helper.** The standard route can write `/tmp`, sees the same files as the elevated route, and honours the same locks. The helper keeps its files, the runner's jobs roots and the release under the base folder set by `CPS_VM_BASE` (default `~/cps`). The `vm.sh` launcher does not carry that variable, so every command would have to set it. The runner writes to the jobs root it is given (the job folders and a temporary `.validate_` folder), to the qualification ledger the release names, and to temporary folders under `TMPDIR`. Its tools keep `$HOME`, except LibreOffice and `pdftoppm` in visual QA, which get a temporary one. Reading the code does not settle whether Chromium (the view screenshots), node or git try to write under `$HOME`, or whether fontconfig needs to update its cache in `~/cps-tools`. If none of them does, a run with its base under `/tmp` needs no elevated route and goes through no automatic review. Only `session_start.sh` would need the elevated route, when it runs the light setup, which writes `~/cps-tools` and runs again after a reset and whenever the named commit changes. M012 tests this with the runner's own test suite, run entirely through the standard route under `/tmp`. If it fails, every helper command uses the elevated route, and the README must say that a request stopped in review has not run: retry it once, then ask the owner.
